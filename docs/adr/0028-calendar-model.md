# 0028. Calendar: events in the database, shaped like iCalendar; CalDAV later

- Status: Accepted (2026-10-15).

## Context

Phase 5 ends with a calendar. The owner decided to ship it inside Alcove first (web and app, stored in
the database like notes, [ADR 0027](0027-notes-in-the-database.md)) and to add CalDAV in a later release,
so that DAVx⁵, iOS Calendar and Thunderbird can sync with it. The model chosen now must map onto
iCalendar (RFC 5545) without a data migration when CalDAV arrives.

## Decision

- **Collections** (migration `1791741600_calendar`):
  - `calendars`: `owner`, `name` (unique per owner, case-insensitive), `color` (the tag palette:
    gray, red, orange, yellow, green, teal, blue, violet, pink; clients map it to design tokens),
    `is_default` (at most one per owner, enforced by a partial unique index).
  - `events`: `owner`, `calendar`, `title`, `description`, `location`, `start`, `end`, `all_day`,
    `rrule`, `uid`, `created`, `updated`. Deleting a calendar deletes its events.
- **Rules**: every read and write is restricted to the owner; the owner cannot be changed, nor an
  event's `uid`. `internal/calendar` checks that an event's calendar belongs to its owner (ids are not
  secret), that it does not end before it starts, that an all-day event covers whole dates, and that
  `UNTIL` has the value type of the start (a date for all-day events, a UTC date-time otherwise). No
  custom endpoint: clients use PocketBase's record API and its realtime subscriptions.
- **Times**: `start` and `end` are UTC instants, shown in the device's time zone. **All-day events** are
  dates: `start` is the first day at 00:00Z and `end` the day after the last one, exclusive, like
  iCalendar's `DTSTART;VALUE=DATE` / `DTEND`. Clients read them as dates (the UTC calendar day), never as
  instants, so a birthday stays on its day in every time zone.
- **Recurrence**: `rrule` holds an RFC 5545 RRULE. The server accepts only the subset clients edit and
  expand: `FREQ=DAILY|WEEKLY|MONTHLY|YEARLY`, optionally `;COUNT=n` (1–999) or `;UNTIL=` (a date for
  all-day events, a UTC date-time otherwise). Clients expand occurrences for the visible range with a
  small function of their own (no date library); days a month lacks (31 April, 29 February) are
  skipped, as RFC 5545 says. A timed series stops at the exact `UNTIL` instant; the editor shows and
  writes it as a last day (the end of that local day). Editing or deleting a recurring event applies to the whole series.
- **uid**: a stable iCalendar UID, generated by the server when the client sends none
  (`<random>@alcove`), unique per owner. It will be the CalDAV resource name.
- **Default calendar**: clients create it (`is_default: true`, named "Personal" in the user's
  language) the first time the user opens the calendar and has none. The one-default-per-owner index
  makes two devices doing it at once, even in different languages, end with one: the second create
  fails and the client reads the list again. A server hook was not used because the server does not
  know the user's language; the stored name is the one of the first device, and the user can rename it.
- `/health` advertises the `calendar` module.

## Consequences

- ✅ Each event maps to one `VEVENT`: `UID`, `SUMMARY`, `DESCRIPTION`, `LOCATION`, `DTSTART`/`DTEND`
  (UTC or `VALUE=DATE`), `RRULE`, `CREATED`, `LAST-MODIFIED`. A calendar maps to a CalDAV collection.
- ✅ Realtime, backups and per-user isolation come from PocketBase like for notes.
- ⚠️ **CalDAV is deferred.** Native apps cannot sync yet. When it comes: a `/dav/` handler (PROPFIND,
  REPORT, GET/PUT/DELETE of `.ics`), ETags from `updated`, a sync token, app passwords for clients that
  cannot do 2FA, and import of rules outside the subset (a wider `rrule` pattern, by a new migration).
- ⚠️ **No time zone per event.** Repeating timed events are expanded in the viewer's time zone, keeping
  their local clock time across DST changes; two devices in different zones may disagree for a series.
  CalDAV will need a `tzid` field (iCalendar `TZID`), added by a migration.
- ⚠️ **No exceptions in a series** (`EXDATE`, `RECURRENCE-ID`): moving or cancelling one occurrence is
  not possible yet. They come with CalDAV, which needs them for imported calendars.
- ⚠️ No reminders, invitations, attendees or sharing between accounts yet.
- ⚠️ Clients load all of a user's events (a series needs its first occurrence); a server-side range
  filter can come when calendars hold many thousands of events.
