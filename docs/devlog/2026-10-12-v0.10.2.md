# v0.10.2: Bringing our own ffmpeg

*2026-10-12, Paul Carouge*

v0.10.1 ended with an open question: on Debian 12 and Ubuntu 24.04, the ffmpeg that the installer
fetched from the system was too old for iPhone photos. Documenting the limit was honest, but "most of
your photos have no thumbnail on the most common server systems" is not what easy self-hosting means.

## The idea

The Docker image already has a good ffmpeg: Alpine's, version 8.1. Each release now also publishes that
same ffmpeg for Linux (amd64, arm64 and the Raspberry Pi's armv7), packed with every library it needs and
Alpine's own small program loader. It does not care which distribution it lands on: I tried it on Debian
12, which has no ffmpeg at all, and it read the test HEIC photo and video on all three architectures.

The installer only offers it when the system ffmpeg is missing or too old, puts it next to Alcove's
binary and leaves the system alone. Like the binary, it is listed in the signed checksums and refused if
anything does not match. Updates, from the command line or from the System page, keep it current, so
ffmpeg security fixes now arrive with Alcove updates. On macOS and Windows nothing changes: Homebrew and
winget already ship recent versions.

## The catch

It is not small: about 45 MB to download, 90 MB on disk. Most of it is video encoders (H.265, AV1) that
Alcove never uses but that Alpine's ffmpeg is linked against. Removing them would mean building ffmpeg
ourselves, and using the distribution's packages unchanged felt more trustworthy than saving 30 MB.

And an update is always performed by the version you are leaving. A server on 0.10.1 updating to 0.10.2
runs 0.10.1's update code, which knows nothing about the bundle. So `sudo alcove update` now also
installs ffmpeg when Alcove is already up to date: one extra command, once, for servers installed before
today.

## What went wrong

- Building the bundles on my Mac, the first archive vanished: Docker runs in a small Linux VM here that
  only sees my home folder, not the temporary directory I wrote to. The script did its job and threw the
  result away.
- The Raspberry Pi build did not start at all: Apple chips cannot run 32-bit ARM programs, even under
  Linux. Installing an emulator in the VM fixed it, and the release machines use one too.
- The pre-commit checks lint the whole tree, so my plan of five tiny commits did not compile one at a
  time. Three commits it is.
