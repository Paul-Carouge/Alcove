# v0.18.1: Real photos, real bugs

*2026-10-12, Paul Carouge*

I put a few dozen photos from my phone on my development server, and the timeline answered with a row of
grey squares: every HEIC picture had failed. All the tests were green.

## Tiles

The HEIC test file had been made on a Mac with `sips`, and it contained one image. A phone camera does
something else: a 12-megapixel photo is stored as dozens of 512×512 tiles plus instructions to assemble
them. ffmpeg understands that, and assembles the tiles itself, in what it calls a stream group. Asking it to
resize "the video stream" at the same time is a contradiction it refuses, with a message that explains
nothing: `Error opening output files: Invalid argument`.

The fix is to ask ffmpeg to resize the assembled group. To make sure it stays fixed, the tests now include a
tiled HEIC built with libheif, from a synthetic picture, so no real photo ends up in the repository.

## Metadata where nobody looks

With thumbnails working, the photos still had no date and no camera. The files came from an OPPO Find X9
Pro (Android, not an iPhone), whose camera software stores the EXIF block of its HEIC files where the
metadata library does not look; macOS's own indexer could not find it either. exiftool could. Alcove now
does what exiftool does when the usual path finds nothing: it looks for the EXIF block in the file itself.
When a HEIC says nothing about its size, the size comes from the tile grid.

## Fixing what already failed

Failed photos were only retried once a night. An update now retries them at start-up, so this release fixes
existing libraries as soon as it is installed: here, all fourteen photos came back with thumbnails, dates
and the right camera name.

Thanks to real photos: no amount of synthetic test data would have found these.
