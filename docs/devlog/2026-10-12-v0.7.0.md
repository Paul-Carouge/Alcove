# v0.7.0: A second lock on the door

*2026-10-12, Paul Carouge*

**Authenticator apps.** Accounts can now require a code from Aegis, 2FAS, Google Authenticator or any
TOTP app. Setting it up is the familiar dance: scan a QR code (or type the key), confirm with a first
code, and save ten recovery codes that work once each if the phone is lost.

**Details that matter.** The secret never sits in the database in clear: it is encrypted with a server
key, either `ALCOVE_SECRET_KEY` or a key file generated once in the data directory. Recovery codes are
stored as hashes. A code is accepted only once (each 30-second window can be used a single time), with
one window of tolerance for clocks that drift. Turning two-factor off, or regenerating recovery codes,
asks for the password and a code again.

**The subtle one.** PocketBase runs its sign-in hook *before* checking the password. A naive hook would
answer "two-factor required" to anyone typing a valid email address, revealing who has it enabled, and
would let attackers probe codes without knowing the password. The hook therefore checks the password
first and only then asks for the second factor. The email one-time code path is closed too, so it
cannot be used to skip the authenticator.

**What went wrong.** Mostly the tests, and in a good way: the rate limiter stopped the unit tests after
five sign-ins in a minute, exactly as it should stop an attacker. The end-to-end test computes real
codes from the key shown on screen, which caught a missed wait before reading the recovery codes.
