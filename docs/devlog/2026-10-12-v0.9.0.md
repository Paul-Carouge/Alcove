# v0.9.0: One command to install, one to update

*2026-10-12, Paul Carouge*

**Why now, before photos.** Self-hosting only works if it stays easy after day one. Every feature from
here on reaches people through updates, so installing and updating had to be as simple as possible
first.

**Installing.** `curl … | sh` downloads the binary for your machine (Linux, macOS, Windows, x86 or ARM,
Raspberry Pi included), checks it, and asks one question: will you reach Alcove from the internet with a
domain (automatic HTTPS, no Docker, no Caddy), from your local network or Tailscale, or behind your own
proxy? It creates a dedicated system user, a hardened service, offers to install ffmpeg, and prints the
setup link. Docker remains a first-class alternative.

**Updating.** `sudo alcove update`, or one click on the new System page. Either way the same steps run:
download, verify, back up the database, swap the binary, restart. The command line also watches the
new version start and rolls back on its own, binary and database, if it does not.

**Trust.** A server that updates itself is only as safe as what it downloads. Each release now ships a
checksum list signed with an Ed25519 key that only the maintainer holds; its public half is compiled into
Alcove, and nothing is installed unless both the signature and the checksum match.

**Testing it like a user would.** The whole flow ran in throwaway containers against a fake release
server: a Debian with real systemd and an Alpine with OpenRC, the one-line install, an update, a
deliberately broken release (rolled back automatically) and a forged one (refused). That caught three
real bugs before anyone met them: the installer crashed when run without a terminal (cloud-init, CI),
the service could not read its own configuration folder, and Alpine put the service user in the wrong
group. Writing OpenRC support came out of the same test: a real Alpine server does not use systemd.

**Next.** Phase 2: photos and videos, with ffmpeg bundled.
