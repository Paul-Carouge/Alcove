# v0.32.0: Bringing Google Photos home

*2026-10-17, Paul Carouge*

The question was simple: can I bring all my Google Photos into Alcove? Since March 2025, Google's API only
lets an app read the photos it created itself, so there is no "connect your account" button to build.
The one complete way out is Google Takeout: a set of zip archives, up to 50 GB each.

## What Takeout gives you, and what it hides

Takeout puts the photos in folders by year and by album, and the information Google knows about each photo
(when it was taken, where, its description, whether it is a favorite or in the trash) in a JSON file next
to it. Uploading the photos alone would lose all of that for every picture without camera data:
screenshots, WhatsApp photos, scans, many videos. They would all be dated the day of the import.

The importer reads the zips directly, without unpacking them to disk, pairs each photo with its JSON and
writes Google's information into Alcove's database. The files themselves are never touched. A plausible
EXIF date still wins; Google's date fills the gaps.

Pairing is the hard part, because Takeout's naming is full of traps: JSON files in a different archive
than their photo, names cut at 46 or 47 characters, `photo(1).jpg` matching `photo.jpg(1).json`, a
`.supplemental-metadata` suffix itself truncated in five different ways, edited copies called `-edited` or
`-modifié` depending on the account's language, and Live Photos split in two. Each case has a test built
from a tiny hand-made archive.

Albums come back as Alcove albums. Photos already in the account, from the phone backup or an earlier
run, are recognized by their fingerprint, so running the import twice adds nothing.

## What went wrong

A feature that unpacks 50 GB archives sent from the outside got three rounds of review, and each one found
real problems.

The first security audit found that a crafted archive could exhaust the server's memory before any limit
was checked, and that the server would then crash again at every restart while retrying the job; and that
any account could fill the disk with import uploads that count against no quota. The fixes: limits on the
zip directory, per-account caps on archives, a free-space margin checked on every chunk, and a job that
gives up after three crashes.

The code review found that saving a large video held the database's only write connection for the whole
copy, freezing every other user; that the hourly cleanup could delete the first archives while the last
ones were still uploading (ten 50 GB archives take more than a day); and that a failed import deleted the
uploaded archives. Archives are now kept until an import succeeds, and listed again after a page reload.

The last review found that the hand-written check of the zip directory did not read the directory where
Go's own zip reader does, and proved it with a crafted file that passed the check with "zero entries". The
check was replaced by a reader that simply refuses to give Go's zip parser more than 48 MB while it reads
the directory, whatever offsets the file claims.

One fix overreached on the way: the free-space margin first applied to every upload, which would have
blocked a Raspberry Pi with a small SD card. Regular uploads and phone backups now only keep 1% (at least
512 MB) free; the 5 GB margin is for imports.

## Limits

A Live Photo comes in as two items side by side, and an edited copy next to its original: Alcove has no
way yet to group items. Album descriptions and comments are not imported.
