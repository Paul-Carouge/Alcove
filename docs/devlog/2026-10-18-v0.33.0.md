# v0.33.0: Tokens that expire, queues that overflow

*2026-10-18, Paul Carouge*

## What

The Android app can now select several photos in the timeline: press and hold one, tap the others, then
favorite, share or move them all to the trash. The release also fixes a blank-timeline bug and carries a
pass on robustness for small self-hosted servers, especially ones keeping their data on a hard disk.

## Why

**Blank thumbnails after the viewer.** File URLs carry a PocketBase file token that expires after about
three minutes, but the timeline built its URLs once per page. The viewer's large previews push the
thumbnails out of Flutter's image cache, so coming back reloaded them with a dead token: blank grid.
Images now go through a provider that asks the session for a fresh token at load time, and whose cache
key ignores the token, so a renewed token never downloads (and makes the server read from disk) an image
already in memory. Concurrent token requests from a grid of thumbnails share one call, and a token is
never reused after a sign-out or server change. Videos had the same problem and now take a fresh token
when they open.

**Keyset paging.** The timeline asked for page N with an offset: once photos were trashed, the next page
started too far and skipped some. It now continues after the last photo shown, without counting the
library on each page. A matching index `(owner, taken_at, id)` lets SQLite read the timeline in order
instead of sorting every photo on every page, which on a cold hard disk meant thousands of random reads.

**Queues that overflow.** The media and documents workers drop items when their queue (4096) is full,
expecting the next restart to pick them up. A big LAN upload or a Takeout import is faster than two
workers, so thousands of photos waited without thumbnails, and an import waiting for them never ended.
A sweep now requeues pending items every five minutes once the queue has drained, with a record of what
is queued or being processed so nothing is handled twice.

**Smaller things.** The server tested for ffmpeg only after copying the whole video to a temp file, every
night, for every video, on servers without ffmpeg. Uploads from the app had no timeout, so a connection
lost while changing Wi-Fi froze the upload queue for hours.

## What went wrong

The review caught three real issues in the first draft: the new image provider never removed failed
images from the cache (Flutter keeps failures unless the provider evicts them), so a photo opened offline
stayed broken; renewing the viewer's token when the page changed was too late, because the next page is
built during the swipe; and the migration's `down` dropped a status index that an older migration owns.
It also found a window where a sweep could queue an item a worker had just taken, and a possible send on
a closed queue at shutdown, both closed in this release.

Left for later, from the audit: a disk cache for thumbnails in the app, passing originals to ffmpeg
without a temp copy on local storage, one ffmpeg run for both thumbnail and preview, and how long web
file tokens should live (longer tokens let the browser cache thumbnails, at a security cost).
