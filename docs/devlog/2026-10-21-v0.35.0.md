# v0.35.0: Borrowed accessibility

_2026-10-21, Paul Carouge_

## What

The web app's drop-down lists (`Select`), action menus (`ActionsMenu`) and account menu (`UserMenu`) now
wrap [bits-ui](https://bits-ui.com) primitives instead of hand-written code. Pages did not change: each
component kept its props. The styling is still plain CSS with design tokens. The decision is
[ADR 0031](../adr/0031-web-headless-primitives-bits-ui.md).

## Why

**Too much CSS, or too much JavaScript?** The question started as "should we move to Tailwind, or
shadcn-svelte?". Measured, the styles were about 7,100 lines over 65 components, but plain scoped CSS
with tokens is idiomatic Svelte, and Tailwind would have moved those lines into class lists rather than
removed them. shadcn's default look would also have fought the product's own art direction. The code
that was actually delicate was elsewhere: every popup re-implemented the WAI-ARIA keyboard model,
focus return, outside clicks and viewport placement, 250 lines for `Select` alone. bits-ui gives those
behaviours without any styling, so it replaces the risky part and leaves the design alone.

**Native where native is enough.** `Dialog` keeps the native `<dialog>`: the browser already provides
the focus trap, Esc and an inert background.

## What went wrong

The first build of the new `Select` failed two end-to-end tests: bits-ui renders its trigger as a plain
button, while the WAI-ARIA pattern (and our tests) expect a combobox. The trigger now keeps
`role="combobox"` and `aria-controls`.

A second trap: lists and menus are portalled to `<body>`, but a modal `<dialog>` lives in the top layer
and makes `<body>` inert, so a list opened from the share-album dialog would have been hidden and dead.
They are now portalled into the enclosing dialog.

The review found four more gaps, fixed before release. Lists inside a dialog were positioned
`absolute`, so near its bottom edge they would have stretched the dialog instead of floating over it.
The account panel was announced as a dialog without a name. Tab dropped the highlighted choice and
Home/End did nothing on a closed list, both regressions from the old component. Long lists had no
scrollbar, as bits-ui hides it in favour of scroll buttons we had not rendered.

Left for later: the Home/End behaviour replays the key once the list is open, which relies on bits-ui
internals and must be rechecked on upgrades. Screen readers were not tested by hand, only through the
axe audits of the end-to-end suite.
